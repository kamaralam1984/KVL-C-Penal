# KVL Hosting Panel — Phase 08 Report: Customer Database Management

## 1. Phase summary
Customer MariaDB/MySQL and PostgreSQL databases, strictly separate from the control-plane PostgreSQL: provisioning with least-privilege users, credential rotation (password shown once), connection info without secrets, backup/restore request workflow, destructive-action safeguards.

## 2. Requirements completed
- Engine availability from the server (`db.detect_engines` -> `server_runtimes` rows `mariadb`/`postgresql`), honest `not_configured`/`not_reported`.
- Provision (`db.provision`): database `<label>_<6hex>` + user `<db>_app`; MariaDB: single `GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, INDEX, ALTER, REFERENCES, CREATE TEMPORARY TABLES, LOCK TABLES ON \`db\`.*` (underscore escaped so it cannot match sibling databases), never `ALL`/`GRANT OPTION`/`*.*`; PostgreSQL: NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOREPLICATION role, database owned by it, `REVOKE ALL ... FROM PUBLIC`. Extra users (read-only or read/write) via `db.create_user`; last read/write user cannot be removed.
- Passwords: generated by the panel (`token_urlsafe(24)`), returned once in the create/rotate/retry response, never stored (job params are scrubbed after the job finishes; verified by dumping every relevant table in tests). Rotation via `db.rotate_password`.
- Agent safety: identifiers must match `^[a-z][a-z0-9_]{2,31}$` AND the panel-managed pattern (so `root`, `postgres`, `mysql` can never be targeted), passwords must match `^[A-Za-z0-9_-]{24,64}$` and are quoted/escaped; SQL is passed in a 0600 script file inside the sandbox (never argv, never shell), admin credentials come from a defaults file/env on the server (never from params, never returned), PG password via `PGPASSWORD` env; errors are redacted with the password; dry-run supported; drop requires `confirm_name == db_name`.
- Provisioning failure: agent drops anything half-created and reports `cleaned_up`; the API additionally enqueues an idempotent `db.drop` cleanup and records the outcome; failed databases can be retried (fresh credentials) or removed.
- No server: database record `pending_server`, no credentials issued; retry endpoint issues them once a server exists.
- Backup/restore request records: `requested -> approved -> running -> succeeded/failed` (+ `rejected`); backups of own data auto-approve for users holding `backups:write`; restores need a succeeded, checksum-verified backup of the same database, then explicit approval with typed database name; agent refuses a restore whose file checksum differs (`integrity_failed`, database untouched). `db.dump`/`db.restore` ops are enqueued only; the backup engine can replace them.
- Destructive safeguards: `destroy-token` (10-minute, single-use, hashed) + typed name + a verified backup from the last 7 days (not required for never-provisioned/failed databases); failure returns the database to `ready`; quota released only after the agent confirms the drop.
- History: `resource_events` per database; quota `databases`; size via `db.size`.

## 13. Known issues and limitations
- No real MariaDB/PostgreSQL was exercised; SQL is validated by builder unit tests and a scripted client, not by a live server. Run a real smoke test on the private server before use.
- Remote access is intentionally off (`@'localhost'` users, local listener); there is no firewall/remote-host feature.
- PostgreSQL read-only/extra-user default privileges assume the primary owner role `<db>_app`.
- Restore approval is by the tenant itself (`backups:restore`) plus typed confirmation; there is no four-eyes rule. Restores overwrite data in place (no automatic pre-restore snapshot besides requiring a prior verified backup).
- `db.dump`/`db.restore` are registered by this module only when no other module has registered them first (module load order); if the backup engine registers them later, reconcile the schemas (`engine, db_name, artifact[, checksum]`).
- Backup files stay under the agent sandbox `backups/db/`; off-site copy/encryption belong to the backup engine.
- Database list has no per-row user count (drawer only).
